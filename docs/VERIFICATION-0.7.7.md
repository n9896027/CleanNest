# CleanNest 0.7.7 本机验证报告

日期：2026-08-27

版本：0.7.7（Build 34）

范围：本地模型证据拓扑、平台适配、控制边界、启停诊断和睡眠/唤醒复核

## 结论

0.7.7 把“能否连上 AI”扩展为一张可解释的本机运行拓扑。用户能同时看到平台、服务地址、模型短 ID、实际 TCP 客户端、launchd 守护和可控范围。只有当前用户且身份证据充足的进程才能进入确认后关闭；其他用户、系统或身份不足的实例只读。

## 自动化证据

- Xcode 工具链全量执行 163 项测试，0 失败，1 项需显式开启的真机 Ollama 测试在普通套件中跳过。
- 同一项 Ollama 测试以 `CLEANNEST_RUN_OLLAMA_INTEGRATION=1` 单独执行通过，耗时约 1.1 秒。
- `CleanNestSelfTest` 全部通过；Release App、登录项、扫描 XPC 与只读 MCP 完成稳定本地签名并通过严格嵌套验证。
- 最终 App 已重新启动为 0.7.7（Build 34）；启动后一次即时样本为 0.0% CPU、约 195 MiB RSS。这只是短程样本，不代替 0.7.9 的长时稳定性门。
- 新回归覆盖：五个平台适配器、Ollama/OpenAI API 风格、TCP 实连解析、当前/其他用户控制边界、用户 LaunchAgent 权限、启动前端口冲突、拓扑结构、PID 替换和模型列表变化。
- 外部关闭的旧回归已增加当前 UID 证据；缺少 UID 或归属其他用户时明确拒绝。

## Ollama 真机空服务闭环

- 执行前确认 `127.0.0.1:11434` 无监听，本机 Ollama 客户端版本为 0.20.0-rc1。
- 测试使用独立临时模型目录启动 `/opt/homebrew/bin/ollama serve`，只绑定回环端口，没有下载或加载任何模型。
- `LocalModelRuntimeDiscovery` 确认了测试创建的精确 PID、当前 UID、11434 监听、Ollama 平台 API 和“没有模型驻留”问题。
- 由于 `/api/ps` 没有运行中模型，快照保持“待确认”，没有把空服务冒充为健康推理实例。
- 测试只正常终止自己持有的进程，再次发现确认该 PID 和 11434 监听都已移除；测试后端口实测已释放。

## 用户可见结果

- 顶部证据卡和每个运行实例使用同一份快照，不再由设置页和运行中心各自猜测状态。
- 每个实例显示控制等级、精确客户端名/PID、守护标签以及端口冲突、短 ID 不匹配、自动重启、实连中断和局域网暴露风险。
- 启动失败、进程替换、模型列表变化和唤醒复核进入本次运行诊断时间线。
- 界面将 oMLX API `id` 明确写为短 ID；模型文件路径只用于 CleanNest 自启，不会发到 API 的 `model` 字段。
- 已生成并目测 [1280×900 宽窗口](evidence/0.7.7/local-model-runtime.png) 与 [900×700 紧凑窗口](evidence/0.7.7/local-model-runtime-compact.png) 演示截图。紧凑宽度下，证据链自动切为 2×2，运行拓扑改为纵向行，守护标签、监听地址和模型短 ID 不再以中间省略号隐藏。

## 安全与证据边界

- 不扫描局域网，只探测已识别进程端口、平台默认回环端口和用户明确配置的回环端口。
- 局域网暴露只告警，不改防火墙、监听地址、模型设置或守护文件。
- 运行拓扑、连接和诊断时间线只保留在当前 App 内存；不保存内网地址、命令行、模型 ID 或客户端连接历史。
- 当前 oMLX 守护继续保持用户先前选择的停用状态；本轮没有启动 27B 模型或改变守护配置。

## 未冒充完成的门

- Ollama 本轮是真实空服务，不是已加载模型的健康推理实例。
- oMLX 的真实守护发现/停用证据来自 0.5.3；本轮为保持用户当前停用选择，没有重新启用。
- MLX-LM、LM Studio 与 llama.cpp 已有适配器和确定性测试，但没有当前 Mac 的真实正向服务样本；不宣称这三个平台的全闭环验收已完成。
- 本轮已完成两种宽度的窗口级视觉回归，但没有完成 VoiceOver 全流程、全键盘操作或多语言长文案真机回归；这些继续作为 0.7.9 发布候选门。
- 本报告不代表 GitHub PR、合并、tag、Developer ID 签名、Apple 公证或公开 Release 已完成。
