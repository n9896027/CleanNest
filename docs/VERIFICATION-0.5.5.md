# CleanNest 0.5.5 本机验证报告

验证日期：2026-08-26
版本：0.5.5（Build 19）
范围：清理扫描内存、重复文件证明链、后台监测频率、取消语义与本地签名 App

## 结论

0.5.5 已完成并通过当前 Mac 的完整只读扫描。相同扫描结果下，最终构建的 CleanNest RSS 峰值为 229,072 KiB（约 224 MiB），扫描后物理占用约 131 MB；不再复现数 GB 的空闲分配区滞留。扫描、哈希与界面结果一致，本轮没有选择、移动或删除任何文件。

这不等于 48 小时常驻耐久测试已经完成，也不等于 XPC 扫描隔离已经落地。高成本扫描迁入独立 XPC 服务仍是后续架构工作，不冒充 0.5.5 能力。

- oMLX 用户守护保持停用，`127.0.0.1:8080` 没有监听服务；验证没有启动本地模型。

## 内存实测

测量对象均为 `build/CleanNest.app` 的真实签名进程，使用相同用户目录和相同扫描选项：

| 指标 | 中间实现（仍使用 Foundation 分块读取） | 0.5.5 最终实现 |
| --- | ---: | ---: |
| 扫描前 RSS | 约 196 MiB | 195,392 KiB（约 191 MiB） |
| 扫描 RSS 峰值 | 4,875,648 KiB（约 4.65 GiB） | 229,072 KiB（约 224 MiB） |
| 扫描后 RSS | 约 4.65 GiB | 223,136 KiB（约 218 MiB） |
| 扫描后物理占用 | 2,150 MB | 131 MB |
| 生命周期物理峰值 | 4,656 MB | 398 MB |
| 空闲 `MALLOC_SMALL` 驻留 | 约 2.0 GB | 约 1.2 MB |

隔离扫描在关闭媒体与重复检测后，RSS 峰值为 223,424 KiB，确认数 GB 峰值来自 Foundation `FileHandle` / `Data` 的重复大文件分块读取，而不是列表 UI 或目录大小统计。最终完整 SHA-256 改用单个 256 KiB POSIX 缓冲区后，完整扫描峰值与无哈希隔离扫描基本一致。

生命周期物理峰值包含 SwiftUI 冷启动阶段，不应解释为扫描单独新增 398 MB；扫描期间的高频 RSS 采样峰值是 229,072 KiB。

## 实现与安全不变量

- 可重建缓存与个人文件扫描串行运行，每阶段结束后请求归还空闲分配页。
- 递归体积统计使用 `fts` 的物理遍历，不跟随符号链接，也不为每个条目创建带资源缓存的 URL。
- 个人文件枚举按 256 项排空临时 Foundation 对象，长期记录只保留路径和值类型身份。
- 重复检测使用“逻辑大小 → 首尾各 64 KiB 指纹 → 完整 SHA-256”；局部指纹只负责排除，不具备证明资格。
- 完整哈希使用 `O_NOFOLLOW` 打开普通文件和单个 256 KiB 缓冲区；执行前仍重新核验候选、保留副本身份与完整 SHA-256。
- 磁盘分析在创建 detached 扫描器前检查父任务取消状态，已取消的请求不会再返回完整报告。
- 实时系统样本每轮只发布一个一致主事件；本地模型发现根据页面、运行状态、菜单栏设置和 App 活跃状态在 10–60 秒间自适应。
