# CleanNest 0.12.0 路线图：清理证据、复核与恢复

状态：P0 代码、自动化和隔离 Home 中的真实 Debug 界面验收已完成；版本元数据已统一为 0.12.0（Build 50），进入发布候选流程。Developer ID Application／Installer 私钥和 `CleanNestNotary` 前置检查已通过，但勾选不代表最终提交、CI、Intel 真机、0.12.0 安装包、公证或公开 Release 已经完成。

## 版本目标与安全边界

Build 49 已有扫描身份复核、重复文件保留项校验和移入废纸篓通道，但通用清理仍缺少统一的活跃文件门、被拦截项的补证据入口，以及与最终 APFS 结果和恢复记录对应的执行账本。0.12.0 优先补齐这些证据链，不以扩大删除范围为目标。

- 扫描、AI 或用户勾选都不直接授予删除权限；执行前仍复核路径、身份和最新活跃状态。
- 打开文件表不可用时失败关闭，不把“没有证据”写成“没有活跃文件”。
- 不自动结束用户进程，不永久删除，不增加“全局绕过安全规则”。
- `lsof` 只提供当前用户、当前时刻的打开文件证据，不等于完整的项目引用图；模型配置引用和容器归属另行验证并分别展示。
- 清理仍只移入废纸篓。所谓释放空间必须区分“已移出原位置”和“清空废纸篓后的最终 APFS 可用空间”。

## 开发任务、验收夹具与顺序

### P0-A：统一清理执行前活跃检查

开发任务：

- [x] 抽象通用 `lsof` 快照与目标匹配，覆盖目标本身和严格后代，避免相似路径前缀误伤。
- [x] 在通用清理的批次开始前检查一次，并在每个项目真实移动前重新取证。
- [x] 活跃文件或探测失败均阻止对应执行，返回进程名、PID、路径和“文件未移动”的可诊断原因。
- [x] 保留已有路径、扫描身份、重复副本与保留项校验；身份变化不能被新预检掩盖。
- [x] 沿用现有清理失败汇总和技术详情展示，不另造一套执行状态。

验收夹具：

- [x] 临时 Home／`Library/Caches` 中无活跃记录的项目可以移入测试废纸篓。
- [x] 目标文件本身、目标目录后代被打开时，原路径仍存在。
- [x] `Cache` 与 `Cache-copy`、兄弟目录不会因字符串前缀产生误判。
- [x] 探测非零退出／不可用时失败关闭。
- [x] 批次预检通过后，单项移动前新出现活跃记录时仍拒绝。
- [x] 已变化的扫描身份仍返回 `.targetChanged`，且源文件保留。
- [x] 混合批次只拒绝活跃项，非活跃项仍进入沙箱废纸篓，不错误归因兄弟路径。

完成结果：10 项定向夹具通过；真实 Debug 界面中的混合执行也确认活跃项保留、非活跃项移入隔离废纸篓。本项不宣称覆盖内存映射、其他用户进程或内核消费者等所有活跃形式。

### P0-B：被拦截项的逐路径复核

开发任务：

- [x] 把清理失败项和扫描保护项形成统一、可定位的复核列表，显示触发的具体规则与已有证据。
- [x] 允许用户重新扫描、重新取得权限或补充限定证据；证据变化后重新生成候选身份。
- [x] 复核只能改变单个明确路径的处置结论，不扩大根目录权限，不提供全局跳过安全门。
- [x] 活跃检查、身份复核和执行前重新验证仍不可绕过。

验收夹具：

- [x] 权限不足、目标变化、活跃文件、保留副本变化分别进入对应原因，而非统一“操作失败”。
- [x] 修复临时夹具中的原因后仅该项目可重试，其他被拦截项保持原状。
- [x] 未补证据、证据过期和指向范围外路径均不能转为可执行。
- [x] 扫描器保留危险根目录、不可读、符号链接、包边界、云端占位、深度与文件上限等逐路径证据；单个扫描器最多记录 200 条。
- [x] 扫描保护项只能定位、打开权限设置或重新扫描，不能直接重试移动；旧扫描 JSON 缺少 `issues` 时仍兼容解码。

完成结果：8 项复核 reducer 测试、4 项扫描保护证据测试通过；真实 Debug 界面已验证活跃消失后的单项重试、重新扫描和符号链接保护边界，并确认权限入口只打开系统设置、不改授权。

### P0-C：通用清理执行账本、最终对账与恢复

开发任务：

- [x] 为每个执行项持久化源路径、实际废纸篓目标、扫描身份、完成状态、错误和时间。
- [x] 清理结束与废纸篓变化后重新读取 APFS 可用空间，分别展示移入量、即时增量和最终可确认增量。
- [x] 提供逐项恢复记录；仅对身份一致且仍位于当前用户废纸篓的项目发起恢复，冲突时停止并说明。
- [x] 中断、部分失败、重复恢复和废纸篓被外部修改均不能生成虚假成功记录。

验收夹具：

- [x] 两个临时候选一成一败，账本准确记录原路径与实际目标，失败项没有伪造目标。
- [x] 移入后伪造或延迟的 APFS 数值不被写成最终释放量；只有相关废纸篓项目消失后才生成最终观测。
- [x] 正常恢复、目标重名、目标身份变化、源位置已存在和记录损坏都有确定结果。
- [x] 应用重启后能读取未完成记录，重复恢复不会覆盖其他文件。
- [x] 系统假成功、目标缺失或身份不符进入 `indeterminate`，不写成已移入；恢复活动不增加“清理项目”统计。

完成结果：活动记录、磁盘对账和恢复账本使用同一执行 ID；6 项账本定向测试通过。真实 Debug 界面已将 Active、Batch 两项恢复到原位置，账本为 `restored`，恢复不增加清理执行数；最终观测明确包含同期系统变化，不作独占归因。

### P0-D：项目引用与特殊占用证据

开发任务：

- [x] 对模型项目检查限定目录内 JSON、YAML、TOML 等配置引用，区分路径文本、真实存在目标和解析失败。
- [x] 为指定应用容器建立专用只读归属与退出状态流程，不把容器整体当作普通缓存。
- [x] 对稀疏文件同时展示逻辑大小与实际分配，避免大数字误导。
- [x] 增加 APFS 容器、快照、重要用途可用容量与废纸篓占用的只读诊断，证据不足时明确显示未知。

验收夹具：

- [x] 相对路径、绝对路径、转义、缺失文件、错误语法和目录穿越引用均有固定样本。
- [x] 配置引用命中时项目保持复核或保护；解析失败不自动扩大为可清理，预览量和执行候选均归零。
- [x] 容器 Bundle ID、签名声明共享组、稳定身份和退出状态分别记录；运行中、归属不明或退出状态未知均保持只读。
- [x] 稀疏文件与 APFS 测试数据只读验证，不为测试删除真实快照或容器。
- [x] 命令不存在、非零、超时、空输出、超大输出和不可解析输出均显示未知；只保留有界摘要，不保留整份原始命令输出。

完成结果：9 项配置引用测试、25 项 Agent 回归、4 项容器测试、4 项应用依赖图回归、7 项 APFS／稀疏文件测试通过。真实 Debug 界面显示五卷 APFS 摘要、0 个本地快照，以及稀疏文件逻辑 134.2 MB／实际分配 16 KB；稀疏差额没有作为可释放空间。引用检查与活跃检查分别呈现，任何单项证据都不被宣称为“绝对安全”。

## 实施顺序

1. **P0-A 执行门**：先阻止正在使用的文件被移动，建立后续工作包都必须复用的执行前边界。
2. **P0-B 精确复核**：让保护原因可见、可补证据，但不绕过 P0-A。
3. **P0-C 执行账本**：把执行、对账和恢复串成同一证据链，再向用户承诺空间结果。
4. **P0-D 专项证据**：最后扩大“能解释的项目”，而不是扩大“能删除的范围”。

每个工作包均先写可丢弃夹具，再实现，再运行定向测试、`swift test` 和 `swift run CleanNestSelfTest`。只有实际执行过的门才可标记通过；崩溃、测试失败或夹具未清理都需如实记录。
