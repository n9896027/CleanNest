# 维护与运营手册

本文档说明维护者如何让仓库、候选版和公开发布保持可审计，不包含任何凭据值。

## 日常变更

1. 从最新 `main` 创建独立分支，不直接改主分支。
2. 实施前确认工作区无无关修改；提交前审查 diff 和凭据扫描结果。
3. 本机运行 `swift test`、`swift run CleanNestSelfTest`、脚本语法和资源格式检查。
4. 使用 Draft PR 获取 CI、CodeQL 和依赖审查结果；检查未完成或有未解决评审时不合并。
5. 只有维护者明确授权后才合并、打 tag 或发布 Release。

## CI 故障分类

- **编译 / 测试**：在本机复现并修复根因；不通过重试掩盖稳定失败。
- **CodeQL / 依赖审查**：先判断数据流与实际可达性，修复或提供可审计的误报理由；不整体关闭检查。
- **外部服务 / runner**：保留失败证据，确认是临时平台故障后才重试。
- **签名 / 公证**：不回退到含糊凭据或把 ad-hoc 产物冒充正式安装包。

## 凭据与供应链

- 仓库不保存 token、签名私钥、公证密码或模型访问凭据。
- GitHub Actions 使用最小权限，Action 引用固定到完整提交 SHA，更新由 Dependabot 提议。
- 签名和公证使用本机 Keychain 或 GitHub 加密 Secrets；日志中只输出身份名称和验证结果。
- 发布产物必须附带版本、提交 SHA、架构、SHA-256 和 SBOM；来源声明不替代 Apple 签名与公证。

## 发布与回退

完整流程见 [RELEASING.md](RELEASING.md)。已公开的 tag 和 Release 不移动；发现缺陷时停止继续分发、在发布说明中标记影响，然后以新版本修复。如果只发布源码，必须明确说明没有 Developer ID 签名和 Apple 公证的官方 App 下载。

## 安全事件

1. 使用 GitHub 私密漏洞报告接收和讨论未公开问题。
2. 如凭据可能暴露，先在来源系统撤销和轮换，再清理历史；不只删除最新文件。
3. 评估已发布版本、受影响数据和可利用路径，必要时暂停 Release 下载。
4. 修复后发布安全公告和新版本，不公开仍可用的凭据或不必要的用户细节。
