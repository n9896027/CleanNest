# 故障排查

## Mole CLI 尚未连接

- 在设置页点“重新检测”。CleanNest 会查找 `mo` 和 `mole` 的常见 Homebrew、MacPorts 与用户本地路径。
- 未安装时可点“通过 Homebrew 免费安装”；这会调用本机 Homebrew 并需要网络。
- 自定义安装请选择实际可执行文件，不要选择所在文件夹。
- 若终端能运行而 App 找不到，通常是图形 App 的 `PATH` 与 shell 不同，直接在设置页选择路径即可。

## 完全磁盘访问反复提示或始终不通过

- 先确认系统授权的是当前运行的 App 副本及路径。
- 不要在 CleanNest 运行时覆盖 `CleanNest.app`；构建脚本会主动拒绝这种操作。
- ad-hoc 重建可能改变代码身份。长期使用请固定路径与稳定签名，详见 [PERMISSIONS.md](PERMISSIONS.md)。
- CleanNest 返回前只复测一次；读取失败后不会再回退到另一套扫描器连续触发系统窗口。

## 磁盘 AI 显示“没有完成”

- 先确认设置页显示本机 AI 已就绪，模型目录包含 `config.json` 和 `.safetensors`。
- 确认服务只监听 `127.0.0.1`，端口与设置一致，并在 `/health`、`/v1/models` 提供兼容响应。
- “模型结果与本机规则冲突”不是权限问题：表示模型建议越过安全边界，CleanNest 已拒绝或改成保守结论。
- 大目录分析只采样有限子项；若信息不足，先进入目标目录再分析会更具体。
- 27B 级模型卡住时检查系统内存压力和交换空间，必要时换更小量化模型。

## 本机模型连接 404、一直转圈或测速失败

- 先查看 `/v1/models` 返回的实际短 ID。oMLX 请求中的 `model` 必须类似 `Qwen3.8-27B-Uncensored-8bit`，不能是 `/Users/...` 文件路径。
- DFlash 开启后仍使用目标模型短 ID；不要填草稿模型路径。CleanNest 只读取服务公布的 ID，不修改 DFlash。
- “模型工作台”只发送一个最小 `OK` 流式请求。健康检查通过但测速失败，通常表示模型 ID、聊天接口、流式事件格式或当前模型载入状态不兼容，而不是文件权限问题。
- 首字与总耗时只代表一次极短请求；模型权重小于物理内存也不保证长上下文或多 App 并行时没有内存压力。

## 磁盘刷新没有重新读取全部内容

- “刷新变化”允许复用 15 分钟内元数据签名未变化的项目，并会显示复用与实扫数量。
- 需要完整重算时，在更多菜单选择“深度刷新（忽略缓存）”。
- 增量索引只保存哈希身份和有界元数据，不保存完整路径或文件正文；可在同一菜单清空。

## 内存数字看不懂或无法关闭进程

- “应用内存”接近进程当前物理占用；“压缩”和“交换空间”反映系统缓解内存压力的方式。
- 绿色压力通常无需为了数字好看而关进程；黄色/红色且交换持续增加时，再优先处理可识别的高占用用户进程。
- CleanNest 默认请求正常退出。PID 身份变化、系统/关键进程、其他用户进程或权限不足都会被拒绝。
- 强制结束可能丢失未保存数据，只在正常退出超时后使用。

## 电池状态未知

- 台式 Mac 没有内置电池时会明确显示“没有内置电池”，属于正常现象。
- 笔记本上先点刷新；原生接口失败时会显示“读取失败”，并在可用时保留 Mole 的数值作为补充。
- 电池信息通常不依赖完全磁盘访问。仍异常时请附 macOS、Mac 型号、Mole 版本和已脱敏技术详情提交 Bug。

## `swift test` 提示找不到 XCTest

安装当前稳定版 Xcode，并在 Xcode 设置中完成组件安装；部分单独或预览版 Command Line Tools 可能没有完整 XCTest SDK。CI 使用完整 GitHub macOS runner 作为合并依据。

## 构建后 App 无法打开

- 源码构建默认可能使用 ad-hoc 签名，适合本机开发但不是公开分发凭据。
- 检查 `codesign --verify --strict build/CleanNest.app` 和系统安全提示。
- 不要从未知第三方下载未公证包；当前官方仓库尚未发布公证二进制。
